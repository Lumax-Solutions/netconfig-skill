2. Prepare recovery before touching SSH.

Keep your current session open and have a provider console or other out-of-band access ready. In a root shell, create a rollback file that **replaces**, rather than merges with, the running rules:

```bash
sudo -i
umask 077
{ printf 'flush ruleset\n'; nft list ruleset; } > /root/nft-before.nft
nft -c -f /root/nft-before.nft
```

Also back up the existing persistent configuration, including any included files.

Arm a system-managed timer that survives SSH disconnection:

```bash
systemd-run --unit=nft-rollback --on-active=5m /usr/sbin/nft -f /root/nft-before.nft
systemctl status nft-rollback.timer
```

Verify the timer is waiting before proceeding. Manual recovery is:

```bash
nft -f /root/nft-before.nft
```

This restores the captured **running rules**, affecting all nftables tables. Avoid concurrent firewall or container-network changes during the window. It does not restore persistent files.

3. Prepare a minimal candidate change.

The following illustrates the intended ordering **inside your existing `inet` input chain**. It is not a complete file or a replacement to paste blindly:

```nft
iifname "lo" accept
ct state invalid drop
ct state established,related accept

ip protocol icmp accept
meta l4proto ipv6-icmp accept

ip saddr 198.51.100.10 tcp dport 22 counter accept
tcp dport 22 counter drop

tcp dport 443 counter accept
```

The chain should ultimately have `policy drop`, after accounting for required existing traffic.

- **Add/reuse** loopback, established/related traffic, and ICMP/ICMPv6 rules. ICMPv6 supports neighbor discovery and path MTU discovery.
- **Add** the restricted SSH allow immediately followed by the SSH drop, before any broader rule that could admit SSH. The drop covers both families.
- **Add/reuse** public TCP/443 access for both families. Add UDP/443 only if you also intend to serve HTTP/3.
- **Modify/remove** conflicting broad accepts and preserve required infrastructure traffic, such as DHCP/DHCPv6. Preserve existing output, forwarding, and NAT behavior.

An accept in one base chain does not override a drop in another. Inspect all relevant chains; adding a separate table alone may not produce the intended result.

Existing connections survive because of the established rule, including previously established SSH from other sources. The restriction applies to **new connections**.

Check and load the reviewed candidate as one transaction, with rollback still armed:

```bash
sudo nft -c -f /root/nft-change.nft
sudo nft -f /root/nft-change.nft
```

`nft-change.nft` represents your prepared, reviewed change file. Syntax checking does not prove connectivity. Do not globally flush the live rules as a separate step.

Disable SSH connection multiplexing when testing, for example with `ssh -o ControlMaster=no -o ControlPath=none …`, so you actually create a new connection. Check rule counters as well.

Only after these tests pass, update the existing boot-time configuration and check it with `nft -c -f`. Ubuntu’s nftables service normally loads `/etc/nftables.conf`; verify its unit and enable it if this is your chosen firewall manager. Avoid blindly saving rules generated by other services.

Then cancel the rollback before its deadline:

```bash
sudo systemctl stop nft-rollback.timer
sudo systemctl is-active nft-rollback.timer
```

Expect `inactive`. If access fails, let the timer restore the previous running rules, then reassess through the console.
